# Native data

Bytes of an export that no tagged property accounts for (mesh and texture data, compiled Blueprint classes, import data) are not opaque. This page lists what the plugin reads in them. A range is *explained* in the Save Analysis only when the reader accounts for its last byte; otherwise the range stays "native / undecoded" and the diff says how many bytes changed.

## What is read

| Data | What the diff can tell you | Read on the engine content |
|---|---|---|
| [Classes and functions](#classes-and-functions) | Variables, functions, flags, interfaces added or changed | every generated class checked against the editor |
| [Function bytecode](#function-bytecode) | Statements added, removed or replaced | 157 functions, 16,351 statements |
| [Graph nodes and pin types](#blueprint-graph-nodes-and-pin-types) | Pins added, removed or changed, with their links and types | 8,873 nodes, 28,854 pins |
| [Texture and mesh sources](#source-data-of-textures-and-meshes) | Source image changed (hash, size, pixels), mesh description geometry and attributes | 7,491 of 7,491 |
| [Cooked textures](#cooked-textures) | Pixel format, mips, which blocks changed, colors, virtual texture chunks | 369 of 369 |
| [Static meshes](#static-meshes) | Material slots, sockets, collision, render LODs, Nanite, distance fields, cards | 1,374 of 1,374 (plugins) |
| [Skeletal meshes](#skeletal-meshes) | Bones, materials, bounds, LODs, sections, vertices | 58 of 58 (plugins) |
| [Morph targets](#morph-targets) | Which LODs' vertex deltas changed | 858 of 858 (plugins) |

The same numbers come from the decoder coverage scan, which lists what could not be read (see [Architecture](Architecture.md#decoder-coverage-scan)).

## Overview

Bytes of an export that no tagged property accounts for (mesh and texture data, compiled Blueprint classes, DNA, import data) cannot be decoded, but they are no longer opaque. Each native range that changed gets its own entry in the diff, with the number of changed bytes, and the Save Analysis counts them as *unexplained* changes. The entry says what the data is for the export's class and gives facts read from its properties, for example `SkeletalMesh: mesh render data (LODs, vertices, skin weights, morph targets) (934,452 of 969,237 bytes are native data). Source LODs: 3, skeleton: ...` or `Texture2D: texture data (mips and platform data). imported size: X=4096 Y=4096, source format: TSF_BGRA8`. The *Changed bytes*, *Explained* and *Unexplained* totals of the Save Analysis (and of the batch and folder reports) now add up the property changes, the header changes and these native changes.

## Classes and functions

The native data of **classes and functions** is read, not only described. A Blueprint's generated class (and any other class or function export) writes, after its tagged properties, its parent, its child functions, the properties it declares (name, type, flags, size, metadata), the size of its bytecode, and for a class its function map, flags, interfaces and default object. The inspector decodes all of that, to the last byte (checked against the running editor: every property of a generated class is found with the type, flags and size the editor reports), and the diff then says what changed in it instead of how many bytes: *Variable NewVar_12* added with its type and flags, a function added to the function map, a flag set, a statement added to the bytecode of a function (see below). The Save Analysis counts such a range as understood (a semantic change with the individual changes listed and its bytes explained). When the data cannot be read to its last byte on both sides (a corrupted or unknown layout), the range stays opaque as before. The data of meshes and textures is still described by class only.

## Function bytecode

The **bytecode** of a function is disassembled, not only measured. A Blueprint graph compiles to a stream of expressions (a token and its operands, which are other expressions, constants, names, and references to objects, functions and properties), and the inspector reads it as the engine does, token by token (`UStruct::SerializeExpr`), into one statement per line of the top level: `LocalFinalFunction(/Script/Engine.KismetSystemLibrary:PrintString, StringConst("Hello"), ...)`, `JumpIfNot(#7, ...)`. Calls, variables and properties are named by path, so the text does not change when the package numbers its objects differently, and a jump names the statement it goes to (`#7`) instead of an offset, so inserting a statement does not change the jumps to the ones after it. The diff then lists the statements that were added, removed or replaced instead of a size. To be sure the reading is right, the size the statements add up to in memory has to be the size the function stores; when it is not, or a token is not known, the bytecode is compared by size as before. On the engine's content, 157 functions with bytecode (16,351 statements) are all read, and the decoder coverage scan reports them (and any that are not) in its *Bytecode* section.

## Source data of textures and meshes

The **source data of textures and meshes** is read as far as the package holds it. A texture keeps its source image outside its properties as editor bulk data (`FEditorBulkData`), and so does the mesh description of a static mesh: the package stores a small record of it (how it is stored, an identifier, the hash of its content and its size), and the pixels or the vertices live in the package, a sidecar file or a virtualization backend. The inspector reads that record, to the last byte (the layouts of `UTexture::Serialize`, `UTexture2D::Serialize`, `UMeshDescriptionBaseBulkData::Serialize` and `FEditorBulkData::Serialize`), and the diff says whether the content changed: *Source image content* from one hash and size to another. Where the data is kept in the file and the identifier a save gives it are not differences, so a resave of the same image reports no change of the source image, with an explanation for the bytes that differ. Packages from before the editor bulk data existed keep the source in the older bulk data format (a header of flags, size and offset, and the payload inline or at the end of the file); that header is read too, with a hash of the bytes as stored, and a resave that only upgraded the format is reported as a change of storage, not of the image. When the source image of a texture changed and the package holds its pixels (in the package trailer, as a save writes them), the pixels are decoded and compared too: the diff says how many pixels differ and where (the bounding box), the largest change of a channel, and the average color of each image. 8 and 16 bit channels and half and full floats are decoded, and the delta transform that a save applies to the pixels is undone; an image compressed as PNG or JPEG is decoded with the engine's own image reader (the red and blue swap that the engine applies to a BGRA PNG is undone) and compared the same way; one that is virtualized or in the older format, one with several slices that is compressed, another size or format, or one larger than 256 MB, is reported as not compared, with the reason. The geometry of a mesh description is decoded the same way: the package holds it in its trailer (or at the offset its record gives), and the inspector deserializes it with the engine's own `FMeshDescription` and the versions of the package. When the content of a mesh description changed, the diff lists the change of its vertex, triangle and polygon counts, of its bounds, and, when the number of vertices is the same, how many vertices moved, the largest move and where they are. The attributes of the corners are compared too: how many normals and tangents changed and the largest turn in degrees, a UV channel added or removed and how many corners of each channel moved, the material slots and how many triangles use another slot. The vertex colors (how many changed and by how much of the range), the sign of the binormals, which edges are hard and the object name of each polygon are compared the same way. A mesh description has no smoothing groups (those exist when a mesh is imported; what it keeps of them is the hardness of the edges). A lightmap texture also writes the flags of its lightmap after the texture's data, which are read and compared. The decoder coverage scan reports these exports too (on the engine content: 4,670 found, 4,670 read; on the engine's plugins: 7,491 found, 7,491 read).

## Cooked textures

A **cooked texture** (saved for a platform, so without its source image) is read to the last byte as well: the layouts of `UTexture2D::Serialize`, `UTexture::SerializeCookedPlatformData` and `FTexturePlatformData`, with the data resource table of the package that locates every mip. The diff lists the pixel format, the size, the slices and cube map, the mips left out by the cook, the mips in the tail, and each mip: its size, whether it is inline or streams from the `.ubulk` (or `.uptnl`) next to the package, and a hash of its pixels, read from the package or from that sidecar file when it is there. Where the pixels are kept in the file moves from cook to cook and is not a difference. When a mip kept its size and storage but its pixels changed, the diff also says which **blocks** of it changed, without decoding the colors: BC and ASTC textures store the pixels in blocks of a fixed size (4 by 4 pixels in 8 or 16 bytes for BC, the block size of the format for ASTC), row after row, so the two versions are compared block by block and the diff reports how many blocks differ, what share of the mip that is, and the box of pixels they cover (uncompressed formats are compared pixel by pixel). For DXT1, DXT3, DXT5, BC4, BC5 and BC7 the colors are decoded too: the diff adds the largest change of a channel over the blocks that differ and the average color of the mip on each side, as stored (no gamma conversion; BC4 is a grey and BC5 has red and green). BC6H and ASTC are compared by blocks only. A mip is only compared when its size is exactly the number of blocks of its format; a layout the reading does not know is reported as not compared. A **virtual texture** keeps tiles instead of mips (`FVirtualTextureBuiltData`): the diff lists its layers and their pixel formats, its size and number of mips, the tile size and border, and each chunk of tiles by the hash and size the engine keeps for it, so changed tiles show without reading the pixels. Platform data stored as derived data references is not read, and the entry says so (on a cook of the engine's own textures: 369 found, 369 read).

## Static meshes

A **static mesh** writes, after its properties, its collision and navigation collision objects, its lighting GUID, its sockets and its **material slots** (the material each slot holds, its slot name, the name it had when it was imported, its overlay material and the texture streaming density of its UV channels). The inspector reads that, to the last byte (the layout of `UStaticMesh::Serialize`, including the fields that older editors wrote and newer ones only read: the package version decides which are there), and the diff lists a slot that was added, removed or given another material, a socket, the collision object and the lighting GUID, instead of an unexplained range of bytes. The geometry of an uncooked mesh is not here: it is the mesh description the source model refers to (read as described above). A **cooked** static mesh keeps its geometry in the **render data** (`FStaticMeshRenderData`), which is read as well: for every LOD its sections (material slot, triangles, vertex range and flags), bounds and deviation, the vertex and index buffers (positions, tangents and UVs, colors, the index buffers) when they are in the export, with the number of vertices, UV channels and indices and a hash of the bytes, or the reference to them when they stream from a sidecar file, then the bounds of the mesh, the screen size at which each LOD is drawn and whether the LODs share static lighting. What lies between the LODs and the bounds is read part by part: the **Nanite resources** (clusters, pages, root pages, the triangles and vertices the mesh was built from, and the pages that stream), the **ray tracing proxy** (whether it exists, how many LODs, whether it shares the buffers of the render LODs), and for each LOD its **card representation** (Lumen: the cards themselves, each an oriented slab with its origin, extent, axes and the side of the mesh it faces, their bounds, and whether the mesh is mostly two sided; a card that moved, was added or was removed is named by its place in the list) and its **distance field** (the bounds, the bricks of each of the three mips, the size of the part that is always loaded, and the streamed mips hashed from the sidecar file). The diff names the part that changed, so a rebuilt distance field shows as *Render LOD 0: distance field* from one count of bricks to another, and a mesh that gained Nanite data as *Nanite resources* from 0 clusters to 6. Each part is also hashed, so a change inside a part that the numbers do not show is still reported. The contents of the Nanite pages, of the buffers of the ray tracing proxy and of the distance field volumes are hashed, not decoded. A layout that is not read (a ray tracing proxy that is inline) falls back to one hash of everything between the LODs and the bounds. The diff names the LOD and the section that changed, so a changed vertex shows as a changed buffer hash with the counts next to it. A mesh saved by an editor from before the mesh description was an object of its own writes the mesh description of each source model inline, in the mesh itself: the inspector reads those (the bulk data in the older format, an identifier and whether it is a hash; the number of source models comes from the `SourceModels` property), and the diff lists a source model whose mesh description has other content, was added or was removed, by the hash of its bytes as stored and its size, without opening the geometry. The identifier a save gives is not a difference. The layout before that stores a raw mesh in its place (the same bulk data, identifier and flag, without the flag in front), which is read the same way and listed as *raw mesh*; only the one that predates the section info map stays unread. On the 184 static meshes of the engine content, all are read; on those of the engine's plugins, 1,374 of 1,374; and on a cook of the engine's own meshes, 85 of 85.

## Skeletal meshes

A **skeletal mesh** is read, and its imported model with it, as far as the layout is known. After its properties it writes its imported bounds, its material slots, its reference skeleton (the bones, each with its parent, its pose and the name it had in the source file), and then the imported model: its LODs, each with its sections, vertices, index buffer and bones. The inspector reads all of it (the layouts of `USkeletalMesh::Serialize`, `FSkeletalMaterial`, `FReferenceSkeleton`, `FSkeletalMeshModel`, `FSkeletalMeshLODModel`, `FSkelMeshSection` and `FSoftSkinVertex`), and the data is *explained* only when the last byte is accounted for. The diff lists a bone that was added, removed, moved to another parent or given another pose, a material slot given another material, changed bounds, and for the model a LOD or a section that was added, removed or changed (its triangles, vertices, bones and flags, with a hash of its vertices, so moved or repainted vertices are reported), and the vertices, indices and bones of a LOD as a whole. The layouts of earlier versions are read as well, back to the 4.2x ones: the raw point indices and the reduction sources of those were blocks of bulk data of their own (the older bulk data format), and their sections have no ray tracing flag. What the reading does not know it does not guess: a mesh with cloth data, skin weight profiles, a layout older still, or the render data of a cooked mesh is read from the start only, the entry says so, and the Save Analysis keeps the changed bytes as unexplained native data. The decoder coverage scan reports skeletal meshes too (on the engine content, all three read to the last byte; on the engine's plugins, all 58).

## Morph targets

The **morph targets** of a skeletal mesh are objects of their own (`UMorphTarget`), and each is read to the last byte (the layouts of `UMorphTarget::Serialize` and `FMorphTargetLODModel`): for every LOD, how many vertices it moves, a hash of those vertex deltas (position, normal and the vertex they apply to), the vertices of the base mesh it was made for, its sections, whether the engine generated it and the file it was imported from. The diff names the LOD whose deltas changed, so a moved vertex shows as a change without listing the deltas. A cooked morph target that stores its deltas compressed, and the layouts from before the sections were saved, are not read, and the entry says so (on the engine's plugins: 858 morph targets found, 858 read).

## Blueprint graph nodes and pin types

The nodes of **Blueprint graphs** are read the same way as classes and functions. A graph node (any `UEdGraphNode`: events, function calls, variable getters, branches, ...) writes its pins after its tagged properties: for each pin its id, name, display name, direction, type, default value, default object and text, links to other pins, sub pins and flags. The inspector reads all of it, to the last byte (checked against the pins the editor holds for a saved graph, and on the nodes of the fixture Blueprints), and the diff lists one change per pin: *Pin Target (links)* with the pin described before and after (`Target (input, object (/Script/Engine.Actor)), linked to K2Node_Event_0.Instigator`), a pin added or removed, a changed default value, type or direction. Pins are matched by their id, so a renamed pin is one change and not a removal and an addition, and the node a link goes to is named through the pins of the node it points at. Events, function entries and results also list the pins the user declared (*Declared pin NewParam*). When the pins are the same and only the bytes differ (a node was added before them and the links, which store the number of the node they go to, were renumbered), no pin is reported and the Save Analysis lists a layout change, not a change of the graph. The texts on a pin (display name, default text) are read by the same decoder as the text properties, so every kind of text history is read; a cast node also writes whether it is pure after its pins, which is read and compared (*Purity*). As with classes, a node whose data cannot be read to its last byte on both sides (a class that writes more than its pins) stays opaque. The decoder coverage scan reports graph nodes too: how many it found, how many it read to the last byte, and the classes and reasons of those it did not (on the 5,261 packages of the engine content: 8,873 nodes, all read, 28,854 pins).

A **pin type** (what a pin of a graph, a variable of a Blueprint or a declared parameter holds) is stored natively too, and it used to be shown as an opaque value that compared equal whatever it held, so changing a variable from `Name` to `Integer` was missing from the Blueprint's `NewVariables` in the diff (only the generated class showed it). It is now read and described (`name`, `int`, `array of object (/Script/Engine.Actor)`, `map of name to int`, with `by reference`, `const`, `weak`, `object wrapper` (a `TSubclassOf` or soft pointer), `single precision` (a real stored as a float), the member a delegate or function pin refers to and its id when set), and the diff shows the type that changed for the variable that changed.
